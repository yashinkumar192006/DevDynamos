# ContextShield — Authentication & Authorization

> **Status:** Implemented (Prompt 5)  
> **Applies to:** backend API (`/api/v1`), gateway, SDK, React frontend

This document describes how ContextShield verifies **who** is calling
(authentication) and decides **what they may do** (authorization). The two are
deliberately separate systems: authentication never grants data access, and
authorization never reconstructs identity from client input.

---

## 1. Trusted identity model

Every protected request is handled as a **Principal** resolved from a
validated credential plus trusted database state:

| Principal kind | Credential | Resolved from |
|---|---|---|
| `user` (human) | JWT access token (`Authorization: Bearer …`) | `users` table + role assignments |
| `service` (AI agent / backend service) | API key (`X-API-Key: csk_…`) | `service_accounts` table |

Three concepts are kept **distinct** and are never conflated:

1. **Identity** — the Principal (user or service). Proven by credential only.
2. **Purpose** — supplied per request, validated separately by the policy
   layer. It is never used to establish identity.
3. **Target resource** — an argument to authorization checks. It is never
   part of the identity.

### What is never trusted

- `X-User-Id`, `X-Role`, `X-Is-Admin`, `X-Username` or similar headers — **ignored entirely**.
- `role`, `roles`, `user_id`, `is_admin` fields in request bodies — ignored
  (`extra="ignore"` on the login schema; other schemas never declare them).
- Roles embedded in tokens — ContextShield tokens don't contain roles at all.
  Roles and permissions are re-resolved from the database **on every request**,
  so deactivation and permission changes take effect immediately.
- Roles alone as proof of access — a user does not automatically have access
  to every record in their department. Access additionally requires matching
  permissions, and policy decisions on top of that.

## 2. User authentication (JWT)

### 2.1 `POST /api/v1/auth/login`

```json
{
  "username": "sarah.chen",
  "password": "SarahHR@2024!"
}
```

**200 response:**

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs…",
  "token_type": "bearer",
  "expires_in": 1800,
  "user": {
    "id": "…",
    "username": "sarah.chen",
    "email": "sarah.chen@contextshield.dev",
    "full_name": "Sarah Chen",
    "department": "Human Resources",
    "employee_id": "EMP001",
    "is_active": true,
    "roles": [{"name": "hr_manager", "description": "…"}],
    "permissions": [{"resource": "employee_salary", "action": "read"}, …]
  }
}
```

**Failure:** every credential failure (unknown user, wrong password, inactive
account) returns the *same* generic response so account existence is not
disclosed:

```json
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer

{"error": {"type": "AuthenticationError", "detail": "Invalid username or password"}}
```

Login attempts (success **and** failure) are written to the audit trail —
usernames only, never passwords.

**Throttling:** repeated failures for the same username + client address
return `429` with a `Retry-After` header (failure-only sliding window,
`AUTH_RATE_LIMIT_*` settings; a second counter keyed by address caps
username-rotation attempts). Successful sign-ins are never throttled and
clear their own counter. The limiter is per-process and in-memory — see
§10.

### 2.2 Token claims

| Claim | Meaning |
|---|---|
| `sub` | User id (database primary key) |
| `username` | Display only — never used for authorization |
| `iat` / `exp` | Issued-at / expiry (Unix seconds) |
| `jti` | Unique token id |
| `typ` | Always `"access"` |

The token deliberately contains **no roles or permissions**. It is signed with
`JWT_SECRET` (HS256 by default) which lives only in the environment; it is
never logged and never shipped to the frontend build.

### 2.3 Other endpoints

| Endpoint | Auth | Purpose |
|---|---|---|
| `GET /api/v1/auth/me` | Bearer (user) | Current profile with fresh roles/permissions |
| `GET /api/v1/auth/whoami` | Bearer **or** API key | Verified identity behind the credential (user or service) |
| `POST /api/v1/auth/logout` | Bearer (user) | Audit-logged sign-out; client discards the token |
| `GET /api/v1/admin/users` | Role `admin` (or `role:admin` scope) | Server-side role enforcement example |

Access tokens are stateless and short-lived
(`ACCESS_TOKEN_EXPIRE_MINUTES`, default 30). There are **no refresh tokens in
v1** — the frontend returns the user to the login screen when a session
expires.

## 3. Service / agent authentication (API keys)

AI agents and backend services must not impersonate users. Instead they
authenticate as **service accounts**:

```http
GET /api/v1/auth/whoami
X-API-Key: csk_…
```

- Keys are generated by the operator, shown **once**, and stored only as a
  SHA-256 hash (`service_accounts.hashed_key`).
- Keys can be revoked (`is_active = false`) or given an expiry
  (`expires_at`) at creation.
- The `service_accounts.last_used_at` column records the last successful use.
- A service account is **never** a user: user-only endpoints (e.g.
  `/auth/me`) return `403`. A user id in a header is *not* an acceptable way
  for an agent to identify itself.

### Creating a service account

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.create_service_account `
    --name demo-ai-agent `
    --scopes "privacy:request,customer_records:read"
```

### Scopes

Scopes follow the `resource:action` convention and are matched with the same
wildcard rules as user permissions:

| Scope | Grants |
|---|---|
| `*` | Everything |
| `customer_records:read` | Read on `customer_records` only |
| `customer_records:*` | Any action on `customer_records` |
| `customer_records` | Any action on `customer_records` (shorthand) |
| `role:admin` | Satisfies role gates that require `admin` |

## 5. Authorization services

Authentication answers *who* the requester is; the reusable
`AuthorizationService` (`app/services/authorization.py`) answers *what that
identity may do*. It is available to the gateway, the SDK, and API endpoints —
all enforcement points share the same primitives. Every check is
**fail-closed** and returns an `AccessDecision(allowed, reason_code, detail)`:

| Method | Question answered |
|---|---|
| `check_resource_access(principal, resource, action)` | May this identity act on this resource at all? |
| `allowed_operations(principal, resource)` | Which actions (`read`/`write`/`delete`/`aggregate`/`export`) are permitted? |
| `check_field_access(principal, asset, field)` | Is this field readable (asset permission + field exists)? |
| `filter_fields(principal, asset, requested)` | Partition requested fields into `(permitted, denied)` — denied fields are never fetched |
| `check_data_ownership(principal, asset, record_key)` | Is this identity the owner (trusted `employees.user_id` link)? |
| `check_purpose(principal, resource, purpose)` | Is the purpose listed by an active policy and does the principal meet its required role? |
| `get_relevant_policies(resource)` | Which active policies cover this resource? |

Reason codes include `PERMISSION_GRANTED`, `NO_MATCHING_PERMISSION`,
`SCOPE_GRANTED`, `NO_MATCHING_SCOPE`, `FIELD_PERMITTED`, `FIELD_NOT_FOUND`,
`OWNER_MATCH`, `NOT_OWNER`, `RECORD_NOT_FOUND`, `PURPOSE_ALLOWED`,
`PURPOSE_NOT_ALLOWED`, `NO_POLICY_FOR_RESOURCE`.

The RBAC layer is a gate, not the final word: the policy engine (later phase)
narrows scope further with sensitivity, purpose, and minimum-disclosure rules.
Nothing in this layer ever returns data — only decisions about data.

## 6. HTTP semantics

| Status | Meaning | Typical causes |
|---|---|---|
| `401 Unauthorized` | Credential missing, invalid, expired, or ambiguous | No `Authorization` header, bad password, expired/tampered JWT, invalid API key, both credentials supplied |
| `403 Forbidden` | Authenticated but not permitted | Missing role/permission/scope, user-only endpoint called by a service, inactive principal mid-session |

Error bodies use the project-wide shape:

```json
{"error": {"type": "AuthenticationError", "detail": "…"}}
```

`401` responses always carry `WWW-Authenticate: Bearer`. Neither error type
reveals whether a username exists.

## 7. Audit trail

The following are recorded in `audit_events` (never with raw sensitive data
or secrets):

- `LOGIN` — success (with actor) and failure (username only, no password).
- `LOGOUT` — actor + timestamp.
- Denied data access (added by the policy engine in later phases).

## 8. Frontend integration (React)

### 8.1 Flow

1. Login form → `POST /api/v1/auth/login` (JSON).
2. On `200`: keep `access_token` **in memory**, hydrate the UI from the
   returned `user` object (roles/permissions come from the server — the UI
   never decides authorization, it only reflects it).
3. On app load: if a token was kept for the session, call
   `GET /api/v1/auth/me` to hydrate the profile; on `401`, drop the token and
   show the login screen.
4. Every API call sends `Authorization: Bearer <token>` via one shared
   fetch/axios wrapper.
5. On any `401` mid-session: clear the token and redirect to login with a
   "session expired" notice. On `403`: show "not authorized" **without**
   logging the user out.
6. Logout: `POST /api/v1/auth/logout`, then discard the token.

### 8.2 Token storage rules

- **Preferred:** in-memory only (React state/context). A page refresh simply
  asks the user to log in again.
- **Acceptable for development convenience:** `sessionStorage` (cleared when
  the tab closes). Document the trade-off.
- **Never:** `localStorage`, cookies without `HttpOnly`, `IndexedDB`, or any
  permanent storage — no "remember me" for access tokens in v1.
- Never decode the JWT in the frontend to derive roles: call `/me` (or use
  the login response). The server is the only authority.
- Never store passwords or the JWT secret in the frontend bundle.

### 8.3 Sketch

```tsx
// src/auth/AuthContext.tsx — sketch, not production code
const API_URL = import.meta.env.VITE_API_URL ?? "http://localhost:8000";

function AuthProvider({ children }: { children: React.ReactNode }) {
  const [token, setToken] = useState<string | null>(null); // memory only
  const [user, setUser] = useState<UserProfile | null>(null);

  async function login(username: string, password: string) {
    const res = await fetch(`${API_URL}/api/v1/auth/login`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ username, password }),
    });
    if (res.status === 401) throw new Error("Invalid username or password");
    if (!res.ok) throw new Error("Login failed");
    const data = await res.json();
    setToken(data.access_token);
    setUser(data.user); // server-provided roles/permissions
  }

  async function api(path: string, init: RequestInit = {}) {
    const res = await fetch(`${API_URL}${path}`, {
      ...init,
      headers: { ...init.headers, Authorization: `Bearer ${token}` },
    });
    if (res.status === 401) {
      setToken(null);
      setUser(null); // → router redirects to /login ("session expired")
    }
    return res;
  }

  // useEffect(() => { if (token) api("/api/v1/auth/me") … }, []); // hydrate on load

  return <AuthContext.Provider value={{ user, login, api }}>{children}</AuthContext.Provider>;
}
```

CORS is already configured for `http://localhost:5173`
(`CORS_ORIGINS` in `.env`). Locked-down production builds should set the exact
production origin.

## 9. Environment variables

| Variable | Purpose | Notes |
|---|---|---|
| `JWT_SECRET` | HS256 signing secret | Required; generate with `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Never commit a real value. |
| `JWT_ALGORITHM` | Signing algorithm | Default `HS256` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Token lifetime | Default `30` |
| `AUTH_RATE_LIMIT_MAX_FAILURES` | Failed logins per username+address | Default `10` per window |
| `AUTH_RATE_LIMIT_IP_MAX_FAILURES` | Failed logins per client address | Default `50` per window |
| `AUTH_RATE_LIMIT_WINDOW_SECONDS` | Throttling window | Default `60` |
| `AUTH_RATE_LIMIT_ENABLED` | Master switch for login throttling | Default `true`; disable only for load tests |

## 10. v1 limitations (tracked for later phases)

- No refresh tokens; re-login after expiry.
- Logout is audit-only; tokens remain valid until expiry (deactivating the
  user invalidates access immediately, since roles/state are re-resolved per
  request).
- No server-side token denylist (`jti` exists for a future one).
- Login throttling is **per-process and in-memory**: with multiple workers
  or replicas the effective fleet-wide limit multiplies, and limits reset on
  restart. A shared store (e.g. Redis) is required for a global quota.
- The per-address counter uses the socket address (no proxy-header trust
  by design); behind a reverse proxy every client shares the proxy address,
  so the address cap becomes a coarse global cap — size it accordingly or
  terminate rate limiting at the proxy.
